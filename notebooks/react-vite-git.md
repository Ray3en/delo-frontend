# React + Vite и Git: от первой публикации до командной работы

Практическая лекция для начинающих. Сначала мы загрузим приложение в репозиторий GitHub и научимся получать обновления. Затем разберём устройство Git, ветки, merge, pull request и типичные ошибки.

Git хранит историю изменений проекта. GitHub — сервис для хранения удалённых Git-репозиториев и совместной работы. Команды Git в основном одинаковы для GitHub, GitLab и других подобных сервисов; в примерах используем GitHub.

В этой лекции публикуем исходный код в репозитории GitHub.

## Часть 1. Пошаговая инструкция

### 1. Подготовьте инструменты

Понадобятся Git, Node.js с npm, редактор кода и аккаунт GitHub. Команды выполняйте в терминале редактора, Terminal на macOS/Linux или Git Bash на Windows. Не вводите символ `$` перед командами: в документации он иногда обозначает приглашение терминала.

Проверьте установку:

```bash
git --version
node --version
npm --version
```

Если команда не найдена, установите соответствующий инструмент и заново откройте терминал:

- [Git](https://git-scm.com/downloads).
- [Node.js](https://nodejs.org/) — поддерживаемую LTS-версию, совместимую с вашим Vite.
- [GitHub](https://github.com/) — создайте аккаунт.

Требования Vite меняются: перед установкой сверяйтесь с [официальным руководством Vite](https://vite.dev/guide/). Если npm сообщает о несовместимой версии Node.js, сначала обновите Node.js.

Один раз настройте автора коммитов:

```bash
git config --global user.name "Ivan Petrov"
git config --global user.email "ivan@example.com"
git config --global --get user.name
git config --global --get user.email
```

Замените имя и адрес своими. Эти значения записываются в историю и не выполняют вход в GitHub. Для приватности можно взять адрес `noreply` из настроек электронной почты GitHub. Настройка без `--global` действует только в текущем репозитории.

### 2. Создайте приложение или откройте существующее

Если проект уже есть, перейдите в его папку, где находится `package.json`, и пропустите создание.

Для нового React-проекта:

```bash
npm create vite@latest my-react-app -- --template react
cd my-react-app
npm install
npm run dev
```

Для TypeScript вместо `react` используйте шаблон `react-ts`.

Откройте адрес, который покажет Vite. Для остановки сервера нажмите `Ctrl+C`. Все дальнейшие команды выполняются из корня приложения.

Основные файлы:

```text
my-react-app/
  public/             статические ресурсы
  src/                компоненты, стили и логика приложения
  index.html          HTML-точка входа
  package.json        зависимости и команды проекта
  package-lock.json   зафиксированные версии зависимостей npm
  vite.config.js      настройки Vite
  .gitignore          правила исключения файлов из Git
```

Названия конфигурационных файлов могут отличаться, например `vite.config.ts` в TypeScript-проекте.

### 3. Настройте `.gitignore`

Откройте существующий `.gitignore` и дополните его при необходимости. Не удаляйте полезные правила, созданные шаблоном Vite.

```gitignore
# Устанавливаются из package.json и package-lock.json
node_modules/

# Логи и системные файлы
*.log
.DS_Store
Thumbs.db
```

В репозиторий добавляют исходники, `package.json`, `package-lock.json`, конфигурации и README. `package-lock.json` нужно сохранять: он помогает устанавливать одинаковые версии зависимостей.

`.gitignore` не удаляет файлы, которые Git уже отслеживает. Исправление этой ситуации разобрано ниже.

### 4. Создайте локальный репозиторий и первый коммит

Если проект ещё не находится под управлением Git, создайте репозиторий:

```bash
git init -b main
```

Если репозиторий уже существует, повторная инициализация не нужна. Посмотрите текущую ветку через `git branch --show-current` и используйте её имя дальше вместо `main`, если оно отличается.

Команда `git status` показывает текущую ветку, изменённые и подготовленные файлы, а также незавершённые операции. Используйте её, когда нужно понять состояние репозитория; далее не будем повторять её в каждом примере.

Подготовьте первый коммит:

```bash
git add .
git diff --cached --stat
git diff --cached
```

Проверьте список и содержимое подготовленных изменений. Убедитесь, что туда не попали `node_modules` и случайные файлы. Затем сохраните снимок:

```bash
git commit -m "Create React app with Vite"
```

`git add` подготавливает изменения, `git commit` сохраняет их в локальной истории. Ни одна из этих команд пока не отправляет код в интернет.

### 5. Создайте пустой репозиторий на GitHub

На GitHub выберите создание нового репозитория:

1. Назовите его, например `my-react-app`.
2. Выберите видимость: Public для открытого кода или Private для ограниченного доступа.
3. Не добавляйте README, `.gitignore` и лицензию при создании: эти файлы можно добавить в локальном проекте позднее.
4. Создайте репозиторий и скопируйте SSH-адрес.

Пример адреса:

```text
git@github.com:YOUR_USERNAME/my-react-app.git
```

Замените `YOUR_USERNAME` на свой логин. Пустой удалённый репозиторий позволяет отправить существующую локальную историю без столкновения с отдельным начальным коммитом на GitHub.

### 6. Настройте доступ через SSH и отправьте код

SSH позволяет GitHub узнавать ваш компьютер по ключу. Настройка выполняется один раз для каждого компьютера: открытый ключ добавляется в аккаунт GitHub, закрытый остаётся у вас.

**Шаг 1. Проверьте, есть ли ключи.** В Terminal на macOS/Linux или Git Bash на Windows:

```bash
ls -al ~/.ssh
```

Если папки нет, создайте ключ следующим шагом. Если уже есть `id_ed25519` и `id_ed25519.pub`, можно использовать эту пару. Не перезаписывайте существующий ключ: он может использоваться для других подключений.

**Шаг 2. Если ключа нет, создайте его:**

```bash
ssh-keygen -t ed25519 -C "ivan@example.com"
```

Укажите свою почту как подпись ключа. Примите стандартный путь клавишей Enter, если он свободен. При запросе passphrase можно задать защитную фразу для ключа. Это локальная защита ключа, а не пароль аккаунта GitHub.

Появятся два файла:

- `~/.ssh/id_ed25519` — закрытый ключ: не передавайте его другим и не добавляйте в репозиторий.
- `~/.ssh/id_ed25519.pub` — открытый ключ: его нужно добавить на GitHub.

**Шаг 3. Добавьте ключ в SSH-агент.** Для Terminal на macOS/Linux и Git Bash на Windows:

```bash
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519
```

Если ключ защищён фразой, агент запросит её. Эти команды относятся к указанным оболочкам; для PowerShell порядок запуска агента отличается. Если использовали другое имя ключа, замените путь. Подробности для разных систем есть в [инструкции GitHub по SSH-ключам](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/generating-a-new-ssh-key-and-adding-it-to-the-ssh-agent).

**Шаг 4. Добавьте открытый ключ в аккаунт.** Выведите его:

```bash
cat ~/.ssh/id_ed25519.pub
```

Скопируйте всю строку. На GitHub откройте настройки аккаунта: **Settings → SSH and GPG keys → New SSH key**. Укажите название компьютера, тип **Authentication Key**, вставьте открытый ключ и сохраните.

**Шаг 5. Проверьте подключение:**

```bash
ssh -T git@github.com
```

При первом соединении сравните показанный отпечаток сервера с [официальными отпечатками GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/githubs-ssh-key-fingerprints) и подтвердите соединение, если он совпадает. Сообщение об успешной аутентификации с вашим именем означает, что ключ работает. Отсутствие shell-доступа в этом сообщении нормально; проверка может завершиться с кодом 1. См. [проверку SSH-соединения](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/testing-your-ssh-connection).

В адресе `git@github.com:YOUR_USERNAME/my-react-app.git` слово `git` всегда остаётся `git`, а `YOUR_USERNAME` — владелец репозитория. Не заменяйте `git` своим логином.

Свяжите локальный проект с удалённым репозиторием:

```bash
git remote add origin git@github.com:YOUR_USERNAME/my-react-app.git
git remote -v
git push -u origin main
```

`origin` — условное имя удалённого репозитория. Флаг `-u` связывает локальную ветку с удалённой, чтобы следующие отправки можно было выполнять через `git push`.

Обновите страницу репозитория: должны появиться исходники и первый коммит. Подробности этого сценария описаны в [инструкции GitHub по загрузке локального проекта](https://docs.github.com/en/migrations/importing-source-code/using-the-command-line-to-import-source-code/adding-locally-hosted-code-to-github).

### 7. Добавьте README

Создайте `README.md` в корне проекта. Опишите назначение приложения, требования и локальный запуск. Пример содержания:

````markdown
# My React App

Приложение для ведения списка задач на React и Vite.

## Запуск

Требуется совместимая с проектом LTS-версия Node.js.

```bash
npm ci
npm run dev
```

````

Сохраните и отправьте документ:

```bash
git add README.md
git commit -m "Document project setup"
git push
```

### 8. Как отправлять следующие изменения

Для небольшого личного проекта цикл выглядит так:

```bash
# Измените и проверьте приложение
git diff
git add src/App.jsx
git diff --cached
git commit -m "Add task creation form"
git push
```

Вместо `src/App.jsx` укажите изменённые файлы. Если нужно добавить все изменения, можно использовать `git add .`, но обязательно просмотреть подготовленный коммит.

В команде обычно работают через отдельную ветку и pull request — полный сценарий приведён во второй части.

### 9. Клонирование: как скачать репозиторий на другой компьютер

`git clone` скачивает файлы и историю, создаёт локальный репозиторий и обычно настраивает удалённый адрес `origin`.

На новом компьютере сначала настройте SSH по шагам выше. Затем откройте терминал в папке, где хотите хранить проекты:

```bash
git clone git@github.com:YOUR_USERNAME/my-react-app.git
cd my-react-app
git remote -v
npm ci
npm run dev
```

После клонирования не нужны `git init` и повторный `git remote add origin`.

`npm ci` устанавливает зависимости по существующему `package-lock.json`. Если lock-файла нет, используйте `npm install`. Если `npm ci` сообщает, что lock-файл не согласован с `package.json`, выясните причину; при намеренном изменении зависимостей обновите lock-файл через `npm install` и сохраните оба файла в коммите.

Для приватного репозитория SSH-ключ должен быть добавлен в аккаунт с правом доступа. Скачивание ZIP даёт файлы без Git-истории: для разработки и получения обновлений удобнее клонирование.

### 10. `git pull`: как получить свежие изменения

Клонирование обычно делают один раз для новой локальной копии. Затем её обновляют через `git fetch` и `git pull`.

Перед началом работы убедитесь, что ваши изменения сохранены, и обновите основную ветку:

```bash
git switch main
git pull --ff-only origin main
npm ci
```

Выполняйте переключение и обновление при чистом рабочем состоянии. Если зависимости не менялись, повторная установка обычно не нужна; после изменения `package-lock.json` выполните `npm ci`.

`git pull` сначала получает удалённые коммиты, затем интегрирует их в **текущую локальную ветку**. Поэтому `git pull origin main`, выполненный внутри `feature/menu`, обновляет `feature/menu` из удалённой `main`, а не переключает вас в `main`.

Мы явно используем `--ff-only`: обновление произойдёт только тогда, когда локальную ветку можно продвинуть вперёд без объединения разошедшихся историй. Если Git откажется, сначала изучите расхождения, а не запускайте принудительную отправку.

Когда tracking-связь уже настроена, достаточно:

```bash
git pull --ff-only
```

Для отдельного получения информации без изменения файлов:

```bash
git fetch origin
git log --oneline HEAD..origin/main
```

Вторая команда показывает коммиты в `origin/main`, которых нет в текущем `HEAD`; удобнее выполнять её, находясь в локальной `main`.

Если есть незавершённые правки, предпочтительно закончить логическую часть и сделать коммит. Временно отложить работу можно так:

```bash
git stash push -u -m "Work in progress before updating"
git pull --ff-only
git stash pop
```

`-u` включает неотслеживаемые файлы, но не игнорируемые. После `stash pop` возможны конфликты: отложенные изменения тоже нужно согласовать с новыми файлами.

## Часть 2. Теория и материалы для работы с Git

### 11. Рабочая папка, индекс и коммиты

У Git есть три важных уровня:

| Уровень | Что это | Как посмотреть |
| --- | --- | --- |
| Рабочая папка | Файлы, которые вы редактируете | Редактор, `git diff` |
| Индекс, или staging area | Изменения, подготовленные для следующего коммита | `git diff --cached` |
| История | Уже сохранённые коммиты | `git log` |

Переходы между ними:

```text
Редактирование → git add → подготовленные изменения → git commit → история
История локального репозитория → git push → удалённый репозиторий
```

Коммит — снимок состояния отслеживаемых файлов с автором, сообщением и ссылками на родительские коммиты. У него есть идентификатор, например `a1b2c3d`; в примерах это условное сокращение, а не значение для копирования.

Если после `git add` снова изменить файл, последняя правка останется вне индекса. Чтобы включить её в коммит, снова выполните `git add`.

Полезные команды:

```bash
git diff
git diff --cached
git log --oneline --graph --decorate --all
git show HEAD
```

`HEAD` обозначает текущий коммит; обычно он указывает на текущую ветку. `HEAD~1` — её предыдущий коммит по первому родителю.

### 12. Что такое ветка

Ветка — перемещаемый указатель на коммит. Она позволяет развивать отдельную задачу, пока основная версия проекта остаётся доступной в `main`.

```text
A---B---C          main
         \
          D---E   feature/header
```

Создайте ветку от актуальной основной версии:

```bash
git switch main
git pull --ff-only
git switch -c feature/header
```

Теперь редактируйте приложение и сохраните работу:

```bash
git add src/App.jsx
git commit -m "Add page header"
git push -u origin feature/header
```

Имена `feature/header`, `fix/login-error`, `docs/setup` — соглашения для удобства, а не специальные типы веток Git.

Просмотр и переключение:

```bash
git branch
git branch -a
git switch main
git switch feature/header
```

Переключение меняет рабочие файлы под выбранную ветку. Незакоммиченные правки не принадлежат ветке как сохранённая история: они могут перейти при переключении или помешать ему. Перед переключением сохраните нужную работу в коммите или временно отложите её.

### 13. Локальные и удалённые ветки

`main` — локальная ветка. `origin/main` — локальная ссылка, отражающая последнее известное состояние ветки `main` на сервере. Она обновляется при обмене с сервером и не является непрерывным наблюдением за ним.

```bash
git fetch origin
git branch -vv
git remote -v
```

`upstream` в контексте tracking-ветки — ветка, относительно которой Git определяет опережение и отставание и обычно выполняет `pull`. Имя удалённого репозитория `upstream` — отдельное соглашение, часто используемое при работе с fork.

| Команда | Назначение |
| --- | --- |
| `git clone URL` | Создать локальную копию с историей |
| `git fetch origin` | Получить данные с сервера без интеграции в текущую ветку |
| `git pull --ff-only` | Получить изменения и обновить текущую ветку, если допустим fast-forward |
| `git push` | Отправить локальные коммиты в удалённую ветку |

### 14. Merge: объединение веток

`merge` объединяет историю указанной ветки с **текущей** веткой. Если хотите включить `feature/header` в `main`, сначала переключитесь в `main`:

```bash
git switch main
git merge feature/header
```

Это пример локального объединения. В командном проекте основную ветку обычно обновляют через pull request и проверки на GitHub.

Возможны два основных результата:

- **Fast-forward:** если `main` не продвинулась после отделения ветки, указатель можно перенести на последний коммит задачи; отдельный merge-коммит не обязателен.
- **Merge-коммит:** если обе ветки изменились, Git объединяет линии истории коммитом с двумя родителями.

```text
A---B---C-------M   main
     \        /
      D------E     feature/header
```

Чтобы включить свежую `main` в свою рабочую ветку, направление другое:

```bash
git fetch origin
git switch feature/header
git merge origin/main
```

Здесь обновляется `feature/header`, а не `main`.

### 15. Pull request: обсуждение и проверка изменений

Pull request, или PR, — предложение включить изменения одной ветки в другую на GitHub. В GitLab похожий механизм называется merge request. PR — возможность сервиса, а не отдельная команда ядра Git.

Обычный порядок работы:

1. Обновить `main` и создать ветку задачи.
2. Написать код, проверить приложение и сделать коммиты.
3. Отправить ветку через `git push -u origin feature/header`.
4. На GitHub открыть **Compare & pull request** или **Pull requests → New pull request**.
5. Проверить направление: **base: main**, **compare: feature/header**.
6. Описать цель, изменения и проверку; для интерфейса приложить скриншот.
7. Дождаться проверок и ревью, исправить замечания.
8. Объединить PR разрешённым в проекте способом.

Пример описания PR:

```text
Задача: добавить навигацию между разделами.
Изменения: шапка с логотипом и ссылками, адаптация для узкого экрана.
Проверка: локальный запуск через npm run dev; проверка на ширине 375 и 1440 px.
```

Для исправлений не нужно открывать новый PR: сделайте коммит в ту же ветку и выполните `git push`. Открытый PR обновится.

**Ревью** — проверка другим участником: корректность, понятность, соответствие задаче. **CI** — автоматические проверки, например линтер и тесты. Успешный CI и одобрение ревью — разные сигналы; один не заменяет другой.

После объединения PR:

```bash
git switch main
git pull --ff-only
git branch -d feature/header
git fetch --prune
```

`-d` удаляет локальную ветку только при выполнении проверки слияния Git. После squash merge эта проверка иногда отказывает: убедитесь, что результат вошёл в `main`, прежде чем решать вопрос с удалением. Удаление ветки на GitHub не удаляет вашу локальную ветку. `fetch --prune` убирает устаревшие ссылки на удалённые ветки.

### 16. Merge, squash и rebase

На странице PR могут предлагаться разные способы объединения:

| Способ | Что происходит | Когда полезен |
| --- | --- | --- |
| Merge commit | Сохраняет коммиты ветки и создаёт коммит объединения | Важна исходная структура истории |
| Squash and merge | Собирает изменения PR в один новый коммит | Хотят один итоговый коммит на задачу |
| Rebase and merge | Переносит коммиты на вершину целевой ветки с новыми идентификаторами | Нужна линейная история |

Локальный `git rebase` тоже переносит коммиты на новую основу и меняет их идентификаторы. Для начала достаточно понимать merge; rebase следует применять по правилам команды. Не переписывайте общую опубликованную историю без согласования с участниками.

`git push --force` способен перезаписать удалённую историю. Это не универсальное исправление ошибки отправки. `--force-with-lease` добавляет проверку ожидаемого состояния удалённой ветки, но всё равно остаётся операцией переписывания истории.

### 17. Конфликты: почему возникают и как исправлять

Конфликт возникает, когда Git не может автоматически совместить изменения: например, две ветки по-разному изменили одну строку или одна удалила файл, который другая редактировала. Разные строки одного файла часто объединяются автоматически.

После `git merge origin/main` в рабочей ветке файл может выглядеть так:

```jsx
<<<<<<< HEAD
<h1>Мои задачи</h1>
=======
<h1>Список задач</h1>
>>>>>>> origin/main
```

`HEAD` здесь — текущая рабочая ветка, нижний фрагмент — объединяемая `origin/main`. Выберите подходящий вариант или напишите новый, затем полностью удалите маркеры:

```jsx
<h1>Мой список задач</h1>
```

Закончите объединение:

```bash
# Исправьте все конфликтующие файлы
# Для данного примера:
git add src/App.jsx
git diff --cached
git commit
git push
```

Если открыт редактор сообщения коммита, сохраните предложенное сообщение слияния и закройте редактор. Пока merge не завершён, его можно отменить командой `git merge --abort`; надёжнее начинать объединение с чистой рабочей папкой.

При конфликте во время rebase после исправления выполняют `git rebase --continue`, а отменяют операцию через `git rebase --abort`. Не смешивайте инструкции для разных операций: продолжайте или отменяйте именно ту операцию, которую начали.

### 18. Как безопасно отменять изменения

Сначала определите, где находится изменение: в рабочей папке, индексе или уже в истории.

**Убрать файл из подготовленного коммита, сохранив правки** — когда в репозитории уже есть коммиты:

```bash
git restore --staged src/App.jsx
```

**Отменить несохранённые в индексе изменения файла:**

```bash
git diff -- src/App.jsx
git restore src/App.jsx
```

Вторая команда заменяет рабочую версию файла версией из индекса и удаляет соответствующие незакоммиченные правки. Применяйте её только к изменениям, которые действительно не нужны.

**Отменить опубликованный обычный коммит новым коммитом:**

```bash
git log --oneline
git revert a1b2c3d
git push
```

Замените идентификатор реальным. `revert` сохраняет историю и создаёт обратное изменение; возможны конфликты. Для merge-коммита нужны дополнительные решения о родительской линии — не используйте этот пример для него вслепую.

**Дополнить последний локальный, ещё не опубликованный коммит:**

```bash
git add src/App.jsx
git commit --amend --no-edit
```

`amend` создаёт новый коммит вместо прежнего. Для уже опубликованной работы новичку проще добавить обычный исправляющий коммит.

Команды `git reset --hard` и `git clean -fd` могут удалить незакоммиченную работу. Не используйте их как обычный способ «починить Git». Если потерялся указатель на коммит, `git reflog` иногда помогает найти его; несохранённые изменения он не гарантирует восстановить.

### 19. Типичные ошибки и решения

#### `not a git repository`

Вы находитесь вне репозитория. Перейдите в папку приложения. Создавайте репозиторий через `git init -b main` только если его ещё действительно нет. Не инициализируйте случайно домашнюю папку или папку со всеми проектами.

#### `remote origin already exists`

Сначала посмотрите существующий адрес:

```bash
git remote -v
```

Если он неправильный, исправьте:

```bash
git remote set-url origin git@github.com:YOUR_USERNAME/my-react-app.git
```

#### `src refspec main does not match any`

Часто ещё нет первого коммита или ветка называется иначе:

```bash
git branch --show-current
git log -1
```

Сделайте первый коммит при его отсутствии и отправляйте существующую ветку. Не переименовывайте её наугад.

#### `rejected` или `non-fast-forward` при отправке

На сервере есть история, которой нет локально. Получите её и изучите:

```bash
git fetch origin
git log --oneline --graph --decorate --all
```

Если это обычные новые коммиты общей ветки, при чистой рабочей папке объедините их с текущей веткой по правилам проекта, например `git merge origin/main`, затем проверьте результат и отправьте. Если локальная и удалённая истории разошлись, `git pull --ff-only` специально откажется вместо автоматического merge.

Если вы создали README на GitHub отдельно, а локальный проект начал собственную историю, простой путь для новичка — клонировать удалённый репозиторий в новую папку и перенести туда исходники без старой `.git`, `node_modules` и `dist`. Проверьте файлы, создайте коммит и отправьте. Если важна существующая локальная история, сначала разберите способ объединения историй; не удаляйте её и не используйте force push наугад.

#### `Authentication failed`, `Repository not found`, `Permission denied (publickey)`

Проверьте адрес `git remote -v`, аккаунт и доступ к репозиторию. Проверьте SSH-ключ, его добавление в агент и привязку к аккаунту; повторите проверку через `ssh -T git@github.com`. Ошибка доступа не исправляется изменением `user.name`.

#### `node_modules` уже отслеживается

Добавьте правила в `.gitignore`, затем уберите соответствующий путь из индекса, сохранив локальные файлы:

```bash
git rm -r --cached node_modules
git add .gitignore
git commit -m "Stop tracking dependencies"
```

`--cached` убирает каталог из отслеживания Git, но сохраняет его на компьютере.

#### После клонирования приложение не запускается

Проверьте папку с `package.json`, версию Node.js и установку зависимостей. Читайте первую содержательную ошибку в терминале. `node_modules` специально не хранится в репозитории: зависимости нужно установить.

### 20. Fork, права доступа и командные соглашения

Если у вас есть право записи, обычно достаточно ветки в общем репозитории. Если права записи нет, можно создать **fork** — собственный репозиторий на основе чужого — и открыть PR из него в исходный проект.

После клонирования своего fork можно добавить исходный проект как второй remote:

```bash
git remote add upstream git@github.com:ORIGINAL_OWNER/my-react-app.git
git fetch upstream
git switch main
git merge --ff-only upstream/main
git push origin main
```

Этот пример предполагает, что в вашей `main` нет расходящихся собственных коммитов. Работу над задачами держите в отдельных ветках. `origin` здесь указывает на fork, `upstream` — на исходный репозиторий.

В команде заранее договариваются об именах веток, формате коммитов, ревью и способе слияния. Для основной ветки полезны правила защиты: PR, успешные проверки и ограничение прямой записи. Конкретные возможности зависят от сервиса и настроек репозитория.

### 21. Хорошие привычки

- Одна задача — одна ветка; один коммит — понятное логическое изменение.
- Сообщение `Fix empty task submission` полезнее, чем `changes` или `123`.
- Перед коммитом смотрите `git diff --cached`.
- Обновляйте основную ветку перед созданием новой рабочей ветки.
- Храните lock-файл и README вместе с кодом.
- Не смешивайте форматирование всего проекта и небольшое исправление без необходимости: это усложняет ревью.
- Проверяйте изменения при локальном запуске приложения.
- Не считайте Git сохранением всего на диске: игнорируемые и незакоммиченные файлы могут не попасть в историю.

### 22. Практическое упражнение

1. Создайте React + Vite проект и отправьте его в пустой репозиторий.
2. Клонируйте репозиторий в другую папку и запустите через `npm ci` и `npm run dev`.
3. В первой копии создайте ветку `feature/welcome`, измените заголовок и сделайте коммит.
4. Отправьте ветку, откройте PR в `main` и объедините его.
5. Во второй копии выполните `git switch main` и `git pull --ff-only`.
6. Убедитесь, что новый заголовок появился и история содержит обновления.
7. В отдельной учебной ветке измените файл, подготовьте его через `git add`, затем уберите из индекса через `git restore --staged` и сравните подготовленные изменения через `git diff --cached`.

Результат упражнения: вы умеете публиковать исходники, скачивать проект, отправлять изменения через PR и обновлять другую копию.
