Environment Занятие 03

Окружение и программное обеспечение

Environment (окружение) — условия, в которых собирается и работает приложение: операционная система, версии ПО, зависимости, переменные и доступные сервисы.

ПО для занятия

Редактор кода, терминал, Git, Node.js с npm и браузер с DevTools. Docker Desktop понадобится для контейнеров.

Сервисы для публикации

Аккаунты GitHub и Vercel. nginx запустим внутри контейнера, отдельно устанавливать его на компьютер не нужно.

Важно

Версии Node.js и зависимостей должны подходить проекту. Проверяем node --version, npm --version, git --version и docker --version.

Environment Занятие 03

Development, staging и production

Development · разработка

Работа на компьютере разработчика. Vite запускает dev-сервер, обновляет страницу при изменении кода и помогает искать ошибки.

Production · пользователи

Готовая оптимизированная сборка на хостинге. Она обращается к рабочему API и должна открываться по публичному адресу.

Staging — отдельное окружение для проверки перед публикацией. Оно может использовать тестовый API и свою базу данных.

Важно

Один исходный код может работать с разными адресами API. Настройки окружения позволяют менять адрес без правки компонентов.

01 · env Занятие 03

Настройки проекта в .env

.env — текстовый файл с настройками проекта. Храним в нём, например, адрес API, чтобы не прописывать его в компонентах. Файл лежит в корне проекта рядом с package.json.

# .env
VITE_API_URL=https://api.example.com
VITE_ENABLE_STATS=false
const apiUrl = import.meta.env.VITE_API_URL;
const statsEnabled = import.meta.env.VITE_ENABLE_STATS === "true";
Важно

Vite передаёт в браузер переменные с префиксом VITE_. Значения из файла — строки. Пароли и приватные ключи в VITE_* хранить нельзя: они попадут в клиентский код.

env · файлы Занятие 03

Какие файлы читает Vite

.env                    # Общие настройки
.env.local              # Личные настройки для всех режимов
.env.development        # Для npm run dev
.env.development.local  # Личные настройки разработки
.env.production         # Для npm run build
.env.production.local   # Личные настройки production

Для production приоритет растёт так: .env → .env.local → .env.production → .env.production.local. Уже заданные переменные процесса имеют наивысший приоритет.

Важно

При совпадении ключа побеждает значение с большим приоритетом. Остальные ключи сохраняются. local означает личный файл, а не режим разработки. Файлы *.local добавляем в .gitignore.

env · пример Занятие 03

Разные API для разработки и production

# .env.development
VITE_API_URL=http://localhost:4000

# .env.production
VITE_API_URL=https://api.example.com

npm run dev использует development, npm run build — production. Режим можно выбрать явно: npm run build -- --mode staging загрузит файлы .env.staging и .env.staging.local вместе с общими файлами.

Важно

После изменения .env перезапускаем dev-сервер. Для опубликованного сайта нужна новая сборка: Vite подставляет значения в JavaScript во время build. .env.example хранит шаблон настроек без секретов.

env · практика Занятие 03

Сборка с production-настройками

npm ci
npm run build
npm run preview
  • npm ci устанавливает зависимости по package-lock.json.
  • Vite создаёт dist с HTML, JavaScript, CSS и ресурсами.
  • preview позволяет проверить готовую сборку локально. Для постоянного хостинга используем nginx или платформу публикации.
Важно

В клиентском Vite значения подставляются во время сборки. Изменение .env рядом с готовой папкой dist не изменяет сайт.

02 · Docker Занятие 03

Docker Compose: два варианта

Docker запускает приложение в контейнере. Compose описывает его сборку и порты. В обоих вариантах исходники копируются в образ через Dockerfile, без volumes.

Без nginx · разработка

services:
  frontend:
    build: .
    ports:
      - "5173:5173"
FROM node:22-alpine
WORKDIR /app
COPY . .
RUN npm ci
CMD ["npm", "run", "dev", "--", "--host", "0.0.0.0"]

С nginx · production

services:
  frontend:
    build: .
    ports:
      - "8080:80"

Открываем http://localhost:8080. Для этого варианта используем Dockerfile со следующего слайда.

Без nginx открываем http://localhost:5173. Vite работает как dev-сервер.

Docker · production Занятие 03

Dockerfile: сборка и nginx

Этап 1 · сборка

# Этап 1
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

Этап 2 · запуск nginx

# Этап 2
FROM nginx:1.27-alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
Два этапа одного Dockerfile

EXPOSE 80 документирует HTTP-порт контейнера. CMD ["nginx", "-g", "daemon off;"] запускает nginx главным процессом. Обе инструкции завершают второй этап Dockerfile в правой колонке.

Docker · команды Занятие 03

Основные команды Compose

docker compose up -d          # Запустить в фоне
docker compose up -d --build  # Собрать образ и запустить
docker compose ps             # Показать состояние сервисов
docker compose logs -f        # Смотреть логи в реальном времени
docker compose down           # Остановить и удалить контейнеры и сеть

-d оставляет контейнеры работать в фоне после завершения команды. --build запускает сборку образов перед стартом сервисов, для которых указан build. Docker может использовать кеш неизменившихся слоёв.

Важно

После изменения кода или .env для production повторяем up -d --build: Vite должен заново собрать dist. В варианте без nginx --build также нужен после изменения исходников: они хранятся внутри образа. Флаг -f у logs продолжает вывод новых записей.

nginx · SPA Занятие 03

nginx: веб-сервер для React SPA

nginx принимает HTTP-запросы браузера и отдаёт HTML, JavaScript, CSS и изображения из готовой папки dist. Файл nginx.conf лежит рядом с Dockerfile.

server {
  listen 80;
  server_name _;
  root /usr/share/nginx/html;
  index index.html;

  location /assets/ {
    try_files $uri =404;
  }
  location / {
    try_files $uri $uri/ /index.html;
  }
}

root задаёт папку сайта. Для существующих assets nginx отдаёт файл. Для маршрута /tasks/42 возвращает index.html, а React Router выбирает экран.

Важно

Без SPA fallback переход внутри приложения может работать, а обновление /tasks/42 — давать 404. Для отсутствующих assets сохраняем настоящий ответ 404.

04 · GitHub Pages Занятие 03

Статический хостинг GitHub Pages

GitHub Pages публикует статические файлы из репозитория. Подходит для учебного React SPA, портфолио и документации.

Что размещаем

Готовую папку dist: HTML, CSS, JS и изображения. Сборку выполняем локально.

Где работает логика

React выполняется в браузере. Для базы данных и серверных секретов нужен отдельный backend.

Важно

Для сайта проекта адрес обычно имеет вид https://username.github.io/repository/. Имя репозитория становится частью пути к ресурсам.

GitHub Pages · Vite Занятие 03

Настройка base и маршрутов

import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";

export default defineConfig({
  plugins: [react()],
  base: "/task-tracker/",
});

Если репозиторий называется task-tracker, base указывает на /task-tracker/. Для username.github.io или собственного домена обычно используют /.

Важно

GitHub Pages не предоставляет обычный SPA rewrite на index.html. Для простой практики используем HashRouter: адрес будет /task-tracker/#/tasks. При переходе с BrowserRouter меняем оболочку роутера на HashRouter.

GitHub Pages · публикация Занятие 03

Публикация из ветки gh-pages

npm install --save-dev gh-pages
npm run build
npx gh-pages -d dist
  • Команду выполняем в Git-репозитории проекта с настроенным origin и доступом на запись. Она отправляет dist в ветку gh-pages.
  • В Settings → Pages выбираем Deploy from a branch, ветку gh-pages и папку / (root).
  • После публикации открываем адрес сайта, проверяем ресурсы и маршруты. Для обновления повторяем build и gh-pages.
Важно

Значения VITE_* берутся при локальной сборке. При использовании собственного домена проверьте base и настройки домена в Pages.

05 · Vercel Занятие 03

Vercel

Vercel — платформа для публикации веб-приложений. Она получает код из репозитория, выполняет сборку и размещает результат по HTTPS-адресу.

Для Vite-приложения

Платформа устанавливает зависимости, запускает npm run build и публикует папку dist.

Для команды

Изменения в подключённом репозитории могут запускать новые публикации. Для проверки доступны отдельные preview-развёртывания.

Важно

Docker и nginx для этого способа публикации настраивать не требуется. Используем тот же React-проект, но размещение и раздачу файлов выполняет платформа.

Vercel · настройка Занятие 03

Подключение Vite-проекта

  • Создаём проект в Vercel и импортируем нужный GitHub-репозиторий.
  • Выбираем корневую папку приложения. Framework Preset: Vite, Build Command: npm run build, Output Directory: dist.
  • Добавляем VITE_API_URL в Environment Variables для нужных окружений: Production и Preview.
  • Запускаем Deploy и проверяем сайт по выданному адресу.
Важно

На Vercel приложение обычно работает от корня домена: base в Vite должен быть /. Значение /task-tracker/ для GitHub Pages нельзя без проверки переносить в эту сборку.

Vercel · SPA Занятие 03

Маршруты и переменные окружения

// vercel.json в корне проекта
{
  "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}

Для обычного SPA с BrowserRouter rewrite позволяет открыть /tasks/42 напрямую. Пример предназначен для приложения без собственных API-маршрутов на Vercel.

Важно

Production и Preview — окружения платформы. Обычная команда vite build в обоих случаях использует mode=production. Отдельный mode задаётся через --mode. После изменения переменных нужна новая публикация.

Практика Занятие 03

Один проект, несколько способов публикации

  • Создайте .env.example и .env.production с публичным адресом API.
  • Соберите dist и проверьте его через preview.
  • Запустите Compose без nginx для разработки, затем соберите вариант с nginx на localhost:8080.
  • Опубликуйте проект на GitHub Pages с подходящими base и HashRouter.
  • Настройте Vercel, проверьте переменные окружения и прямое открытие маршрута.
Важно

Для каждого варианта проверяем главную страницу, ресурсы, внутренний маршрут и API. Изменённые VITE_* должны попасть в новую сборку.

Итоги Занятие 03

Роли инструментов

.env и Vite

Настройки выбираются для режима сборки. Публичные переменные VITE_* становятся частью клиентского приложения.

Docker и nginx

Docker упаковывает и запускает окружение. nginx принимает HTTP-запросы и отдаёт файлы сайта.

GitHub Pages

Публикует готовую статику из репозитория. Для проекта учитываем путь репозитория и маршрутизацию.

Vercel

Собирает и публикует проект на платформе. Настройки окружения задаём перед сборкой.
